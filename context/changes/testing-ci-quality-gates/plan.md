# CI Quality Gates — Implementation Plan

## Overview

Wire vitest and `astro check` (TypeScript typecheck) into GitHub Actions so the
existing test suite and type system block PR merge on failure. Also close the
final test coverage gap (`campaigns/index.ts`), enable branch protection, and
correct an inaccuracy in `test-plan.md` §5.

This is rollout Phase 4 of `context/foundation/test-plan.md`.

## Current State Analysis

- `.github/workflows/ci.yml` `ci` job runs: `npm ci` → `npx astro sync` →
  `npm run lint` → `npm run build`. No `npm run test` step, no typecheck step.
- The `deploy` job has `needs: ci`, so the CI job is the sole gate for both PR
  checks and production deploys.
- The test suite is hermetic and green: 12 files, 96 tests, 1.15s.
  `tests/setup.ts` mocks `astro:env/server` so no secrets are needed.
- Vitest 4.1.8, `@vitest/coverage-v8`, and `vite-tsconfig-paths` are installed.
  `vitest.config.ts` is present. The `test` npm script (`vitest run`) exists.
- `@astrojs/check` is already in `dependencies`. No `typecheck` npm script
  exists. `astro check` has never been run in CI.
- `tests/integration/api/campaigns-index.test.ts` does not exist.
  `src/pages/api/campaigns/index.ts` (GET list + POST create) has no tests.
- `.husky/pre-commit` runs `npx lint-staged` only (ESLint on staged files).
  There is no `typecheck` or test step in the pre-commit hook.
- `test-plan.md` §5 incorrectly claims "lint + typecheck ... already wired via
  husky + GitHub Actions." Typecheck has never been wired.
- `auth/signout.ts` is a 6-line route not covered by any test file. Cost ×
  signal assessment: low signal, not worth a dedicated test.

### Key Discoveries

- Test step needs **no `env:` block** — `tests/setup.ts:3-7` mocks all secrets.
  Do not add environment variables to the test step.
- `astro check` needs no secrets either — it runs type-checking against the
  type stubs generated by `astro sync`, which already runs as a CI step before
  lint. Ordering is preserved.
- Branch-protection is a **repo-settings concern**, not a workflow file concern.
  Adding the test step makes tests run and report on PRs; the `gh api` command
  in Phase 3 is what makes them block merges.
- `getUserCampaigns` (called by GET handler) queries `supabase.from("campaigns")`
  internally — `makeSupabaseMock({ campaigns: {...} })` covers it via the
  established module-boundary mock pattern.
- The POST insert at `campaigns/index.ts:58-62` ignores `error` and checks only
  `!campaign`. This produces the correct outcome (500 on failure) and is NOT
  the Risk #3 silent-success pattern — there is no bug to fix, only untested
  validation logic to guard.

## Desired End State

Every PR to `main` triggers the `ci` job, which must pass before merge is
allowed. The job runs: lint → typecheck → tests → build. A single failing test
or TypeScript error blocks the merge and the Cloudflare deploy (because
`deploy` has `needs: ci`). The campaigns list/create route has regression
coverage. `test-plan.md` §5 accurately describes what is gated.

### Verification

- `npm run test` exits 0 with ≥13 test files.
- `npm run typecheck` exits 0.
- CI job on a PR shows four visible steps: lint, typecheck, test, build — all
  green.
- GitHub branch-protection for `main` lists `ci` as a required status check.
- A PR with a deliberately failing test cannot be merged via the GitHub UI.

## What We're NOT Doing

- Adding `auth/signout.ts` tests — route is 6 lines with minimal blast radius;
  documented in §7 as an explicit "don't test" decision.
- Adding a pre-push git hook — out of scope; the CI gate is the enforcement
  layer.
- Adding coverage reporting to CI — available via `npm run test:coverage` but
  not required for the gate; can be added later without blocking this phase.
- Changing the Cloudflare deploy workflow — `needs: ci` already makes the
  gate transitive.
- Adding E2E tests — Phase 4 scope is unit/integration coverage + CI wiring.

## Implementation Approach

Three sequential phases: close the coverage gap first so the new tests are
included when the gate locks in; then wire the CI steps; then enable the
branch-protection rule and update documentation.

## Critical Implementation Details

**Pre-flight before Phase 2:** Run `npm run typecheck` locally before adding
`astro check` to `ci.yml`. If it fails due to existing type errors, those must
be resolved before the step is committed — otherwise the first CI run blocks
all PRs. Phase 2 includes a local pre-flight step for exactly this reason.

**`enforce_admins: false` in the `gh api` command** means repo admins can
still force-merge. To require the check for admins too, set it to `true`. The
plan defaults to `false` so the developer retains an escape hatch.

## Phase 1: Add campaigns/index.ts integration test

### Overview

Create `tests/integration/api/campaigns-index.test.ts` covering the GET (list
campaigns) and POST (create campaign) handlers. This closes the last coverage
gap before the CI gate locks in, so the gate immediately includes these routes.

### Changes Required

#### 1. New integration test file

**File**: `tests/integration/api/campaigns-index.test.ts`

**Intent**: Regression-guard the GET and POST handlers on
`src/pages/api/campaigns/index.ts`. Every test must assert from the route's
documented behavior (validation rules, ownership enforcement, error contract) —
not from the implementation. Follow the §6.2 cookbook pattern exactly.

**Contract**:
- Top-level `vi.mock("@/lib/supabase", () => ({ createClient: vi.fn() }))` and
  `vi.mock("@/lib/ai", ...)` (same pattern as all integration tests).
- `beforeEach` calls `vi.resetAllMocks()`.
- `makeContext(options?)` helper defaults to `{ locals: { user: { id: "user-1" } } }`;
  accepts `{ user: null }` for the unauthorized case.
- **GET — required cases**:
  - null Supabase client → 500 with `{ error: "Supabase is not configured" }`
  - no user in locals → 401 `{ error: "Unauthorized" }`
  - `makeSupabaseMock({ campaigns: { data: null, error: { message: "DB error" } } })` → 500
  - happy path `{ data: [{ id: "c-1", name: "My Campaign" }], error: null }` → 200 `{ campaigns: [...] }`
- **POST — required cases**:
  - null client → 500
  - no user → 401
  - invalid JSON body → 400 (pass a non-JSON body in the Request)
  - empty name (or name is whitespace-only after trim) → 400
  - name longer than 200 characters → 400
  - description longer than 500 characters → 400
  - insert fails: `makeSupabaseMock({ campaigns: { data: null, error: { message: "insert error" } } })` → 500
  - happy path → 200 `{ campaign: { id: "c-1", name: "Test Campaign", ... } }`
- POST request stub: `new Request(url, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ name: "Test Campaign" }) })`. Do NOT use `application/x-www-form-urlencoded` — the handler calls `.json()`.
- Oracle: assert against the route's documented validation rules (name required, ≤200, description ≤500), not against the Zod/schema internals.

### Success Criteria

#### Automated Verification

- `npm run test` passes with 13 test files and all tests green

#### Manual Verification

- Test file covers the 5-tier pattern for GET (null client, unauthorized, Supabase error, happy path) and all POST validation branches

## Phase 2: Wire CI gates

### Overview

Add a `typecheck` npm script and insert `npm run typecheck` and `npm run test`
steps into the `ci` job, positioned after lint and before build.

### Changes Required

#### 1. Add typecheck script to package.json

**File**: `package.json`

**Intent**: Expose `astro check` as a named npm script so it can be called
consistently both locally and in CI, and appears alongside the other test
scripts.

**Contract**: In the `"scripts"` block, add `"typecheck": "astro check"` after
`"test:coverage"`. No other changes to `package.json`.

#### 2. Insert typecheck and test steps into ci.yml

**File**: `.github/workflows/ci.yml`

**Intent**: Add the two new CI steps in the `ci` job so every PR triggers
typecheck and vitest before building. The steps must have no `env:` block —
`astro check` needs only the type stubs from `astro sync`; vitest is hermetic.

**Contract**: In the `ci` job, after `- run: npm run lint` and before
`- run: npm run build`, insert:

```yaml
      - run: npm run typecheck
      - run: npm run test
```

No `env:` block on either step. The `npm run build` step that follows already
carries `SUPABASE_URL` and `SUPABASE_KEY`; do not add those to the new steps.

### Success Criteria

#### Automated Verification

- `npm run typecheck` exits 0 locally (pre-flight; resolve any failures before committing)
- `npm run test` exits 0 locally (already confirmed; verify it still passes after Phase 1)
- CI run on a feature branch shows `npm run typecheck` and `npm run test` steps, both green

#### Manual Verification

- Inspect the updated `ci.yml`: no `env:` block on the typecheck or test steps
- Confirm the step order is: lint → typecheck → test → build

## Phase 3: Enable branch protection and update documentation

### Overview

Make the CI gate actually block merges via GitHub branch protection, then
correct `test-plan.md` §5 and add `auth/signout.ts` to §7.

### Changes Required

#### 1. Enable required status check on main

**Intent**: Set GitHub branch protection for `main` so the `ci` check must
pass before any PR can be merged.

**Contract**: Run the following command with a GitHub token that has admin
scope on this repo (the `GITHUB_TOKEN` generated during a workflow run has
admin scope by default if the repo's Actions settings permit it; for a local
run, use `gh auth login` with an admin PAT):

```bash
gh api \
  --method PUT \
  repos/vroobel95/10x-DnD/branches/main/protection \
  --field required_status_checks='{"strict":false,"contexts":["ci"]}' \
  --field enforce_admins=false \
  --field required_pull_request_reviews=null \
  --field restrictions=null
```

`strict: false` requires the `ci` check to pass on the PR branch but does not
require the branch to be up to date with `main` before merging.
`enforce_admins: false` gives repo admins an escape hatch; change to `true` to
enforce for everyone. The `contexts` value must match the GitHub Actions **job
name** exactly — the job is named `ci` at `ci.yml:8`.

To verify the rule is in effect:
```bash
gh api repos/vroobel95/10x-DnD/branches/main/protection \
  --jq '.required_status_checks'
```
Should return `{"strict":false,"contexts":["ci"],"checks":[{"context":"ci",...}]}`.

#### 2. Correct test-plan.md §5 Quality Gates

**File**: `context/foundation/test-plan.md`

**Intent**: Replace the inaccurate §5 table with one that reflects the actual
gate state after Phase 4 ships. The "lint + typecheck already wired" claim is
false; typecheck was never wired before this phase.

**Contract**: Replace the entire §5 table and its content. The corrected table:

| Gate | Where | Required? | Catches |
|---|---|---|---|
| lint (ESLint via lint-staged) | local (on commit) | required | staged-file lint violations |
| lint (ESLint full) | CI on PR | required | all lint violations including unstaged |
| typecheck (`astro check`) | CI on PR | required after §3 Phase 4 | TypeScript type errors in `.astro` and `.ts` files |
| unit + integration (vitest) | CI on PR | required after §3 Phase 4 | logic regressions, silent-failure patterns, invalid stat blocks, IDOR regressions |
| build | CI on PR + push to main | required | build failures, missing env references |
| e2e on auth critical flow | CI on PR | optional — only if no integration seam exists | broken password reset / callback end-to-end |

Remove the separate "ownership boundary tests" and "CI test gate (vitest in
pipeline)" rows — these are now subsumed by the "unit + integration (vitest)"
row.

#### 3. Add auth/signout.ts to test-plan.md §7

**File**: `context/foundation/test-plan.md`

**Intent**: Document the explicit decision not to test `auth/signout.ts`,
matching the §1 cost × signal principle and the existing §7 structure.

**Contract**: Append to the §7 bullet list:

```markdown
- **`auth/signout.ts` null-client fall-through** — the `if (supabase)` guard
  skips `signOut()` and redirects to `/` when the Supabase client is null.
  Blast radius is minimal: worst case is a session cookie that expires naturally.
  The cost of a dedicated test outweighs the signal given this route has no
  validation, no mutation-with-confirmation, and no user-facing data at risk.
  The null-client anti-pattern is documented in `lessons.md` and is already
  guarded in higher-stakes routes (forgot-password, reset-password).
  (Source: Phase 4 research — §1 principle #1 cost × signal.)
```

## Testing Strategy

### Integration Tests (Phase 1)

New file `tests/integration/api/campaigns-index.test.ts`:
- 4 GET cases: null client, unauthorized, Supabase error, happy path
- 7 POST cases: null client, unauthorized, invalid JSON, empty name, name >200, Supabase error, happy path
- Optional: description >500 case (~8th POST test)

### Automated CI verification (Phase 2)

The CI job itself serves as the integration test for the gate: it must show
both `npm run typecheck` and `npm run test` steps in the Actions UI and report
pass/fail on PRs.

### Manual Testing (Phase 3)

A deliberate failing-test PR is the only reliable way to confirm branch
protection is active — the API response alone does not prove the UI blocks
merges.
